去年我接了个小活：给一家电商公司做客服 Agent。你可以把它理解成一个自动回复机器人——用户问商品问题，它从知识库里找答案，自动回。我评估了一下：搭检索链路、调提示词、对接接口，两周搞定，信心满满。

结果上线第一天，客服群里就炸了。

不是我代码有 bug，是**用户的提问方式，完全超出了我的想象**。下面三个场景，每一个都是我亲手踩过的坑。

## 场景一：47 条单字消息，把系统打爆

有个用户连发了 47 条消息，每条就一个字。我的 Agent 把每个字都当成一次独立提问：47 次检索、47 次大模型调用，全部打到上游接口。直接触发了"限流"——简单说就是"你请求太频繁，被拦了"——整个客服系统当场卡死。

我测试的时候，想的全是"用户问：这款鞋防水吗？Agent 答：这款鞋采用 Gore-Tex 材质……"。现实是用户发的是"鞋""子""防""水""吗""贵""不""贵"。

谁测试的时候会想到这个？

## 场景二：整段 HTML 粘进来，检索出 div class

还有个用户，直接把整段商品详情页的 HTML 粘进来了——几千个字符，带着完整的 CSS 样式代码。我的切分策略是按长度切的，这段 HTML 被切成二十几个碎片，每个碎片里都是 `td`、`tr`、`div` 这种标签。

检索的时候，这些标签的"向量"（可以理解为机器用来判断"两句话语义像不像"的特征值）跟正常问题的相似度竟然还挺高。Agent 一本正经地回用户："根据您提供的信息，div class 等于 product-info……"

用户把截图发到客服群，配文：**你们这是请了个程序员当客服？**

我当时看到这条消息，脑子嗡的一下。

## 场景三：embedding 把标签当成正经问题

场景二其实已经点出了最要命的那个坑。向量检索看的是"语义相不相似"，但 HTML 标签里恰好有 `product-info`、`price` 这类词，和"这件衣服多少钱"语义接近，于是被错误召回。模型不是不行，是我压根没想过输入会长成这样。

## 核心真相：能回答 ≠ 能扛住

把三个场景放一起看，你会发现：**没有一个是模型能力问题。** 模型该答的都能答。但真实用户不会按你测试用例的方式提问——他们打字漏字、连环发、复制粘贴、甩一大段网页源码。

你测的是"理想输入"，他们给的是"真实输入"。中间差着的，就是工程该补的洞。

## 小结

- 真实用户不会按测试用例提问：漏字、连发、粘贴大段网页或代码。
- 三个翻车点，没有一个是模型不行，全是"工程没兜底"。
- **能回答**（质量）和**能扛住**（稳定）是两件事，后者靠工程补，不靠模型。
