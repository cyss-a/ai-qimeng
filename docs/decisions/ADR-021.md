# ADR-021: 日报抓取迁 Cloudflare Worker + R2，前端运行时渲染

- 状态：Accepted（2026-08-12）
- 决策者：高见远（首席架构师）
- 关联：ADR-001（Astro 7 静态产物）、ADR-003（静态托管 / GitHub Pages 兜底）、fetch-news.py（既有 build-time 生成器）

## 背景（Context）

M7「AI 热点日报」当前由 GitHub Actions 定时执行 `scripts/fetch-news.py`：从 6 个中文 RSS 源抓取、聚合成 Markdown、提交回仓库、触发 Astro 重建。痛点有二：

1. **抓取端不稳**：GitHub 跑构建的机器位于美国，跨太平洋访问国内源（量子位、机器之心、36氪 等）偶发慢、偶发超时，导致当日日报生成失败或延迟。
2. **更新非实时**：内容依赖「提交 → 重建」链路，最快也要分钟级，且重建受 GitHub Pages 部署队列影响，做不到「每日定时且稳定更新」。

用户决定把「抓取」从 GitHub Actions 迁到 **Cloudflare Worker**（亚太边缘节点，Cron 每天北京时间 09:00 触发），将结果写成 JSON 存入 **R2**；静态站改为**运行时从 R2 拉 JSON 客户端渲染**（免重建、国内 CDN 快、真正每日更新），同时**扩展抓取源到更多国内科技 / AI 媒体**。GitHub Pages 仍作为静态托管（站点真实域名 `cyss-a.github.io/ai-qimeng/`），Cloudflare 仅承担「抓取 + 存储」职责，不接管站点托管。

约束（继承自既有架构）：
- 站点为纯静态、`output: 'static'`，无后端；本 ADR 引入的 Worker/R2 是**离站的数据管线**，不改变站点的静态本质。
- `fetch-news.py` 的健壮性语义（单源失败跳过、当日 < 5 条不覆盖最新）必须保留。
- P0 铁律：禁用 emoji 图标、禁用紫粉渐变、图标/配色一律走 design token，本管线产出的前端渲染层同样遵守。

## 决策（Decision）

采用 **Cloudflare Worker（Cron 触发器）+ R2 存储 + 前端运行时渲染** 替代 GitHub Actions 定时抓取：

1. **抓取层**：新建 Cloudflare Worker，Cron 表达式 `0 1 * * *`（UTC）= 北京时间 09:00，从扩展后的国内源清单（见 `docs/architecture/daily-news-worker.md` §4）并发抓取，归一化为统一 item 结构。
2. **存储层**：Worker 将结果写入 R2 bucket `ai-qimeng-news`，对象布局：
   - `news/latest.json` —— 当日最新（每日覆盖写）
   - `news/YYYY-MM-DD.json` —— 每日归档（保留最近 14 天，过期清理）
   - `news/index.json` —— 可用日期数组（降序，供前端归档用）
3. **渲染层**：`src/pages/m7/index.astro` 保留 build-time 渲染（来自 `fetch-news.py` 生成的 Markdown，作 SEO + 即时可见兜底）；新增一段渐进增强 `<script>`，运行时 `fetch` R2 的 `latest.json`，若其 `date` 新于 build-time 已知日期，则用同一套 `.daily-card` 样式覆盖卡片网格；失败时静默保留 build-time 内容。
4. **跨域**：R2 公开桶配置 CORS，仅允许 `https://cyss-a.github.io` 的 `GET`/`HEAD`（运维 guide 给出 `wrangler r2 bucket cors` 命令）。

## 理由（Arguments）

- **抓取更稳**：Worker 跑在 Cloudflare 亚太边缘（香港 / 新加坡 / 东京等），到国内源的 RTT 远低于 GitHub 的美国机器，跨太平洋链路抖动被规避，单源失败概率下降。
- **更新真正每日化**：JSON 直接写入 R2，前端运行时拉取，绕开「提交 → 重建 → 部署」链路，北京时间 09:00 后用户刷新即见当日内容，无需等站点重建。
- **国内交付快**：R2 经 Cloudflare 全球 CDN 缓存，大陆用户就近（HK/SG 边缘）取到 JSON，比回源 GitHub Pages 更快；静态页本身仍在 GitHub Pages。
- **韧性双保险**：build-time Markdown 兜底保证「即使 Worker/R2/CORS 任一环节故障，日报页仍有内容、可被搜索引擎收录」；Worker JSON 负责「新鲜度」。两者职责分离、互不阻塞。
- **源扩展开销低**：新增源只是在 Worker 的 SOURCE_REGISTRY 加一项，不改变架构；`MIN_ITEMS=5` 下限保证少量源抖动不会污染 `latest.json`。
- **成本可忽略**：Worker 免费额度 10 万次请求/日、R2 免费 10GB 存储 + 百万级操作/月，日级 Cron + 3 个对象的写入与读取用量远低于阈值（详见架构文档 §8）。

## 后果（Consequences）

- 正面：
  - 抓取稳定性与时效性显著提升，不再受 GitHub 美国构建机跨洋访问拖累。
  - 日报内容覆盖更广（源从 6 扩到 ~17），且每日刷新无需重建站点。
  - 静态站点零改动即可获得「运行时新鲜度」，SEO 由 build-time 内容保障。
- 负面 / 约束：
  - 引入 Cloudflare 账号 + 绑卡 + Worker/R2 开通的运维成本（由 devops 同学出步步指引）。
  - 新增一套离站数据管线，需维护源清单、CORS、Cron 三项配置；源清单与 `fetch-news.py` 的原列表需保持同步意识（见架构文档 §9）。
  - 前端需新增一段渐进增强脚本，并遵守「先 build-time 后 runtime 覆盖」的渲染契约（见架构文档 §6），增加少量前端复杂度。
  - R2 公开桶的 CORS 若配错，`fetch` 会被浏览器拦截——但 build-time 兜底保证页面不空白（优雅降级）。
- 风险缓解：
  - **Cloudflare 中国可达性澄清（重要）**：Worker 执行在 Cloudflare 边缘 PoP（亚太为 HK/SG/JP/TW 等），**不是**中国大陆节点（标准套餐无大陆 PoP，大陆需单独的 Cloudflare China 合作方案）。本方案的价值不在于「在大陆执行」，而在于：
    (a) 亚太边缘**抓取**国内源比美国机器更稳更快；
    (b) R2/CDN 把 JSON **投递**到大陆用户时走就近边缘，加载更快。
    站点本身仍由 GitHub Pages 托管，用户加载页 + JSON 的链路不涉及「绕过 GFW」或「大陆内执行」。此 caveat 必须写入用户指引，避免误解。
  - CORS 仅放行 `https://cyss-a.github.io` 的 `GET`/`HEAD`，不加自定义请求头 → 不触发预检（preflight），降低配置敏感度。
  - 可选增强：若 r2.dev 公开桶在生产环境有配额/稳定性顾虑，可让同一个 Worker 增加 `GET /news/*` 路由直接读 R2 并附带 CORS 头返回，彻底免去对 r2.dev 公开桶的依赖（架构文档 §7 备注）。本 ADR 主决策仍为「R2 公开桶 + CORS」，增强作为后续可选。
  - 健壮性完全继承 `fetch-news.py`：单源失败跳过、`< 5` 条不覆盖 `latest.json`，详见架构文档 §5。
